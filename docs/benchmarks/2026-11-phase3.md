# Phase 3: wake latency and false stall wake-ups

Measured 2026-11-08 with `eval/phase3-measure.sh` on the v0.8 watcher in the repo (worker events built, Phase 3a–3f). Two done-when parts, two answers:

| Done-when part | Result |
| --- | --- |
| A Claude worker's handoff wakes Jarvis within one watcher tick | **Pass with `JARVIS_BATCH_SEC=0`, miss with the default batch window** |
| False stall wake-ups for working Claude workers drop 80% against the baseline | **Miss: 0% fewer** (3 of 3 runs wake falsely with events on, and with events off) |

## Method

Every run is a throwaway git repo holding a copy of the template's `handoffs/`, on the **tmux** host, on a tmux server of its own that the script kills by its socket. "Jarvis" is a pane running `cat`, registered with `jarvis start`. The real `jarvis watch` loop runs in a window beside it, and the worker is started by `jarvis spawn`, so the launch script, the run record, `JARVIS_ROLE`/`JARVIS_BRIEF`/`JARVIS_RUN` and the event file are the production ones.

- **Scaled down:** tick `JARVIS_WATCH_SEC=5` (default 60), `JARVIS_STALL_MIN=1` (default 15). Latency is reported in seconds and in ticks. The other settings are the defaults, including `JARVIS_FASTPATH="trust edit nudge"`.
- **Workers:** fake agents, shell scripts registered as the `claude` agent. They make the same `jarvis hook event working|stop|ended` calls Claude Code's hooks make (stdin payloads in the shape of `eval/hook-payloads/`) and hold a changing or frozen screen. Fakes burn no usage, so they are spawned with `--force`, which passes the machine-wide Claude cap; the real worker is spawned without it.
- **Events on / off:** the watcher has no switch for this. It reads the event file when the worker wrote one and falls back to the screen hash when not. So **off** is a worker that makes no hook calls (a repo without the hooks in `.claude/settings.json`), **on** is the same worker making them. The screen hash alone is how the watcher behaved before Phase 3, so the events-off run of each scenario is the comparison.
- **No Phase 0 number exists** for false stall wake-ups: `2026-11-baseline.md` says "not measured yet". This page does not invent one; the events-off run stands in for it.
- **Scenarios**, each ×3 runs with events on and off (the three runs were identical in every count):
  - **a** the worker works 6 s, writes its handoff, ends its turn. Latency from the file being written to the wake text appearing in Jarvis's pane (250 ms polling), once with `JARVIS_BATCH_SEC=0` and once with the batch window scaled the way the default scales (`JARVIS_BATCH_SEC` = one tick, as 60 and 60 by default).
  - **b** a worker that is working but whose screen is frozen for 165 s (a long tool call or a long think), then writes its handoff. Any stall wake-up before the handoff is false.
  - **c** a truly stuck worker: working event, then a frozen screen, no event, no handoff. A stall wake-up is right; events must not hide it.
  - **d** a worker that ends (`ended` event, process gone) without a handoff. A wake-up is right.
- **One real worker** (`claude --model claude-haiku-5-5`, trivial brief: write one file) measured latency only, to show the real hooks fire. The script presses Down and Enter on the trust prompt a fresh folder shows (default highlight is "No, exit"), in that worker's pane only.

## Results

Homebrew bash 5.3 and stock bash 3.2 gave the same counts and timings within 0.3 s.

### 1. Latency: handoff written → Jarvis woken

| Watcher config | Events | Runs | Seconds (min / median / max) | Ticks (median) | Within one tick |
| --- | --- | --- | --- | --- | --- |
| `JARVIS_BATCH_SEC=0` | on | 3 | 2.8 / 3.0 / 3.1 | 0.6 | 3 of 3 |
| `JARVIS_BATCH_SEC=0` | off | 3 | 2.8 / 2.9 / 3.0 | 0.6 | 3 of 3 |
| `JARVIS_BATCH_SEC=5` (one tick) | on | 3 | 8.0 / 8.1 / 8.5 | 1.6 | 0 of 3 |
| `JARVIS_BATCH_SEC=5` (one tick) | off | 3 | 8.0 / 8.2 / 8.2 | 1.6 | 0 of 3 |

(Table is the Homebrew bash run; bash 3.2 was within 0.2 s of every cell.) "Within one tick" allows 1 s on top of the tick for pane polling and `tmux send-keys`.

- With no batch window the wake comes 0.6 ticks after the handoff on average. The lag is the wait for the next tick.
- With the batch window the wake comes 1.6 ticks after, in all six runs: the tick that finds the handoff opens the batch, and the next tick sends it. At the shipped defaults (60 s tick, 60 s batch) that is 60–120 s, not one tick.
- Events on and off are the same, as the code says: a handoff is found by scanning `handoffs/*.md`, not by events. Events don't change this part either way.
- **Real worker:** the Claude Code hooks fired: its event file held `working` and `stop` (in the bash 3.2 run the file was read before `stop` landed, so only `working` was counted). The handoff was written and the watcher woke Jarvis 1–2 s later (whole-second timestamps), with `JARVIS_BATCH_SEC=0`. One worker, so no spread.

### 2. False stall wake-ups

b: a working worker, screen frozen 165 s, then a handoff.

| Events | Stall wake-ups per run | Nudges per run | Where the watcher took it from |
| --- | --- | --- | --- |
| on | 1, 1, 1 (total 3) | 1, 1, 1 | `nudge:screen`, `stall:screen` |
| off | 1, 1, 1 (total 3) | 1, 1, 1 | `nudge:screen`, `stall:screen` |

**Reduction with events on: 0% (target 80%). Miss.**

Why, from `watch.sh` (`watch_tick`): events decide the stall path only when the worker's last event is `stop` or `waiting` (its turn is over). A worker whose last event is `working`, which is what a worker in the middle of a long tool call or a long think has, goes down the same branch as a worker with no events, the frozen-screen check. So with a frozen screen it gets one nudge ("Finish the phase or write your handoff now.", typed into a worker that is working) after `JARVIS_STALL_MIN`, and a stall wake-up after another. Hooks tell the watcher when a turn ends. Nothing in a hooks-based run tells it a turn is still going, so the 80% cut isn't there for this case.

How big the false-stall problem is in real use is a separate question. Claude Code's own screen animates (spinner, elapsed timer) during tool calls and thinking, so a screen that is frozen for 15 minutes while the worker works is rare. The fake agent freezes it on purpose, which tests the code path and gives an upper bound, not a real rate. With no Phase 0 number, 80% of the real rate is not something this run can show.

### 3. The wakes that should still happen

| Scenario | Events | Woke | Seconds from spawn (min / median / max) |
| --- | --- | --- | --- |
| c stuck, frozen, no handoff | on | 3 of 3 | 133.6 / 133.8 / 134.1 |
| c stuck, frozen, no handoff | off | 3 of 3 | 133.4 / 133.6 / 134.5 |
| d ended, no handoff | on | 3 of 3 | 9.5 / 9.6 / 9.6 |
| d ended, no handoff | off | 3 of 3 | 138.7 / 139.0 / 139.5 |

- **Events don't hide a real stall (c):** same wake, same time, either way (nudge after one stall interval, wake after a second: about 2 × 60 s plus ticks).
- **Events help with a worker that exits (d):** Jarvis is told on the next tick, about 10 s after spawn, against about 139 s on the screen hash alone (two stall intervals, nudge then wake). That is the real gain from worker events: 14× sooner for this case. It is a speed gain on a true event, not fewer false wake-ups.

## Not covered

- Only the ended-turn (`stop`, `waiting`), `ended` and handoff paths were driven with deterministic fakes. `permission` events and the fast prompt paths are in `eval/selftest.sh`.
- The real worker is one haiku run per script run; it says the hooks fire and the latency is small, not how latency spreads.
- Scaled settings (5 s tick, 1 min stall) keep the defaults' ratios, but the real values (60 s, 15 min) were not run.
- The 40 labelled terminal tails in `eval/terminals/` (the fallback's regression set) were not touched.

## Reproduce

```
bash eval/phase3-measure.sh        # about 7 minutes; /bin/bash (3.2) works too
P3_REAL=0 bash eval/phase3-measure.sh   # skip the real Claude worker
P3_ONLY="b:on c:off" P3_REPS=1 bash eval/phase3-measure.sh   # a few cells
```

It needs tmux, jq, git, perl and python3, and is read-only for the checkout: it copies `plugins/jarvis/skills/setup/templates/` once, and works in a temp directory it removes (`P3_KEEP=1` keeps it).
